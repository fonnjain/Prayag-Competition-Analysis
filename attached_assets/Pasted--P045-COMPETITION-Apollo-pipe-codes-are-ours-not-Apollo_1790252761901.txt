# P045 — COMPETITION — Apollo pipe codes are ours, not Apollo's

> **P045** · app: **COMPETITION** (`prayag-price.com`)
> **THIS PROMPT CHANGES CODE.** It loads no Apollo data.
> Quote `P045` when reporting back.
> **Nothing Apollo has been loaded yet. This is prevention, not cleanup.**

Prayag have confirmed: **the Apollo item codes for all pipes were generated by hand because the Apollo PDF does not carry them.** The fittings codes are Apollo's own.

Reading the competitor master confirms the split exactly — **354 generated codes, and they are precisely the seven pipe sheets**:

```
AGRI PIPE      APA001-APA123        CPVC PIPE    APC001-APC040
CASING PIPE    APK001-APK018        PPR PIPE     APP001-APP031
SWR PIPE       APS001-APS080        UGD PIPE     APU001-APU010
UPVC PIPE      APU001-APU052
```

Every fittings sheet carries irregular supplier-shaped codes — `CMN020101`, `PPRMB0204XX20MM`, `UM…`, `PT…`, `CTNR…`. Those came from Apollo.

**A generated code is not an identity.** Apollo's next price list will not contain `APC001`, because Apollo has never heard of it. Everything below follows from that.

# Two findings from the first Apollo analysis are withdrawn

## Withdrawn 1 — the `APU001`–`APU010` collision is not an Apollo data error

It was reported as a **BLOCKER**: the same ten codes appear in UGD PIPE and UPVC PIPE against different products and prices — `PU-1` at ₹324 against `U-11C` at ₹2022 — with the action *"Do not load the UGD sheet. Ask Prayag."*

**There is nothing for Prayag to rule on.** UGD and UPVC both took `U` as their letter and both numbered from 001. It is our own scheme colliding with itself. **Withdraw the question. Renumber instead.**

## Withdrawn 2 — "Apollo code but no price" is an artefact

All **77** such rows are in pipe sheets. Every one is a code minted for a row Apollo does not price.

```
SWR PIPE      24 priced    56 minted with no price
PPR PIPE      15 priced    16 minted with no price
CASING PIPE   14 priced     4 minted with no price
UGD PIPE       9 priced     1 minted with no price
```

It never meant "Apollo lists this and the price is missing". It means a number was assigned to nothing. **Drop the category.** Those rows have no Apollo price, and that is the whole of it.

**One genuine Apollo question survives:** `PPRMB0204XX20MM` is quoted at two different prices. That is a real supplier code with a real conflict, and it still needs a ruling.

# PART 1 — A locally assigned code must never look like a supplier code

## 1.1 Record the difference

Every competitor code carries its origin:

```
code_source = 'supplier'          read from the competitor's own document
code_source = 'locally_assigned'  minted here because the document had none
```

Not a naming convention — a stored field. A convention is a habit; a field is a fact, and it survives the next person.

## 1.2 Make it visible

A locally assigned code must be **unmistakable on sight**, in the UI, in every export, and in the competitor master. Anyone looking at a list must be able to tell at a glance which codes came from the supplier.

Choose the treatment and report it. It must not be possible to read a minted code as one of Apollo's.

## 1.3 It must never be presented as the competitor's reference

A locally assigned code is an internal handle. It does not go into anything that reaches Apollo, a customer, or a supplier-facing report as though it were their SKU.

---

# PART 2 — Renumber the collision

`APU` is used by both UGD PIPE and UPVC PIPE, from 001 in each. Ten codes overlap.

Give every sheet a **distinct namespace** and prove it. Report the mapping you choose, old code to new, for all ten affected rows.

**Then make the collision impossible rather than merely fixed:** minting must fail loudly if a generated code already exists anywhere in the competitor set. A scheme that can collide will collide again the next time a category is added.

---

# PART 3 — Matching on the next Apollo load

**This is the part that decides whether the next Apollo file is usable.**

For pipes, the code cannot be the match key. Apollo's next PDF will not contain it, so a code match finds nothing and the loader creates a second parallel set beside this one.

**For rows whose `code_source` is `locally_assigned`, match on normalised description plus size** — not on code. For supplier codes, match on the code as now.

Report:

1. The normalisation you apply to description and size, quoted.
2. What happens when a description matches more than one row.
3. What happens when a description matches nothing — it must become a **new** row, not a silent skip.
4. Proof by loading the same Apollo file **twice**: the second load must create nothing and change nothing. Report the row count before, after the first load, and after the second.

Test 4 is the whole of Part 3. A scheme that cannot survive its own file twice will not survive a revised one.

---

# PART 4 — A code is never minted for a row with no price

77 codes currently exist for rows with no Apollo price.

**No price, no row.** A missing price is a missing price — it is not a product Apollo sells at an unknown price, and it must not become one.

The unpriced rows are **reported** as gaps in Apollo's coverage, listed by category, so the business can see what Apollo does not quote. They do not enter the competitor set and they receive no code.

# Rules

1. **Load no Apollo data in this prompt.** This changes the loader; it does not run it.
2. No Prayag product is created, changed or deleted. A competitor upload must never create a Prayag product, and new-product mode must not be offered on one.

5. No price value is invented. A blank price stays blank.
