## 0. The validation was right to stop, and the problem is bigger than the three rows it found

P061 added 301 "punctuation / case variant matches" to raise coverage. **That was unsafe and is
withdrawn in full.** The validation flagged three of them; there are at least thirteen provably
broken, and the remainder cannot be verified from outside production.

**Failure 1 — the one the validation caught.** `TTS - 01` was matched to ERP `TTS-01`. But `TTS-01`
is itself a separate production product. The ERP row was claimed twice: once by the exact match, once
by the variant. The check for this was never written.

**Failure 2 — worse, and not yet reported.** Five ERP rows were each claimed by **two different
production products**:

| ERP row | Claimed by |
|---|---|
| `322-K` | `322 K` **and** `322K` |
| `323-K` | `323 K` **and** `323K` |
| `324-K` | `324 K` **and** `324K` |
| `325-K` | `325 K` **and** `325K` |
| `326-K` | `326 K` **and** `326K` |

Same pattern in `FT-02M`/`FT-02 M`, `DB-52-3IN-N`/`DB-52-3 IN-N`, `7991F-N`/`7991 F-N`,
`EP-GANESHA`/`EP-Ganesha`.

The ambiguity test in P061 asked whether one production code matched *two ERP rows that disagree*. It
should have asked two further questions: whether the ERP row was already claimed by an exact match,
and whether two production codes claimed the same ERP row. Both go the other direction, and both were
missed.

**50 of the 301 involve production codes carrying internal spaces** — precisely the codes this project
has already established are significant. The conclusion from P057 and P060 §0.2 stands and should
never have been bent: **punctuation and whitespace are significant in these item codes. Exact match
only, everywhere, always.**

## 3. A standing rule to apply from here on

Add this to the project's working rules, not just this prompt:

> **Item codes are matched exactly. Never by normalisation, never by stripping punctuation or
> whitespace, never case-insensitively.** `TTS-01` ≠ `TTS - 01`. `322K` ≠ `322 K`.
> `DB-02L` ≠ `DB-02 L`. This applies to mapping files, loaders, matchers and any future data work.
> Where a normalised form is genuinely needed — fuzzy competitor matching — it is a ranking signal
> only and must never decide that two stored codes are the same product.

If any earlier prompt, file or instruction of mine conflicts with that, this rule wins.
