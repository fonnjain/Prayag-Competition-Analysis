## 0. What the diagnostic changed

The Step-1 output is accepted. It changed three things about the plan, and one of them is a stop.

### 0.1 STOP — the item-code backfill in P057 A.3(a) must not run

P057 said: consolidate `normCode`, re-point `authoritativeCode` at it, "do not backfill existing rows
here." That is no longer sufficient. **Making the loader write the canonical form would violate the
unique index on `catalog_products.item_code`**, because the catalogue already contains pairs that
differ only by internal whitespace:

| Existing code | Existing code | Both normalise to |
|---|---|---|
| `TTS-01` | `TTS - 01` | `TTS-01` |
| `TTS-02` | `TTS - 02` | `TTS-02` |
| `TTS-03` | `TTS - 03` | `TTS-03` |
| `DB-02L` | `DB-02 L` | `DB-02L` |

Those four were found from the handful of codes that happened to appear elsewhere in the Step-1
output. The full collision set across all 7,191 products has not been measured — **§3.1 measures it
before anything else happens.**

Also decisive: **0 orphan matched competitor rows, 0 recoverable by normalisation.** The item-code
spelling differences are *not* breaking any join today. So the correct action is a **code-consistency
fix with no change to stored codes at all**. See §3.

**Amendment to P057 A.3(a):** keep the `normCode` consolidation and the `matchKey` rename. **Do not**
re-point `authoritativeCode` at the canonical `normCode` yet, and do not change what any loader
*stores*. `normCode` is for *comparison and lookup* only until §3 is resolved.

### 0.2 The composite divisions are source data, not a code bug

No pipe-joining code exists. The values arrive already joined inside
`Prayag_MRP_Authoritative_v2_01Sep2026.xlsx`, are read at
`artifacts/api-server/src/lib/authoritativeMrpMaster.ts:345` and written at `:691`, under load batch
17 / `mrp_sources` row 428.

That means the workbook is telling us something true: **these 57 products genuinely sell into more
than one division.** Look at what they are — plastic cisterns, toilet seat covers, cistern internals,
rag bolt assemblies, concealed stop cocks, teflon tape. Of course they appear in two price books.

So **Option 1 (force a single primary division) is the wrong answer.** It would make each of these
products vanish from the other division's browse — which is the same defect that was reported, just
pointed the other way. **Go with Option 2.** §2 implements it.

## 2. Composite divisions → primary + membership (Option 2)

### 2.1 Schema

```sql
CREATE TABLE product_divisions (
  id          serial PRIMARY KEY,
  item_code   text NOT NULL,
  division    text NOT NULL,
  is_primary  boolean NOT NULL DEFAULT false,
  source      text,                      -- 'authoritative-master-batch-17' etc.
  created_at  timestamptz NOT NULL DEFAULT now()
);
CREATE UNIQUE INDEX product_divisions_item_division_idx ON product_divisions (item_code, division);
CREATE INDEX        product_divisions_division_idx      ON product_divisions (division);
CREATE UNIQUE INDEX product_divisions_one_primary_idx   ON product_divisions (item_code)
  WHERE is_primary;
```

Add it to `lib/db/src/schema/catalog.ts` next to `catalogProductsTable`, following the existing
drizzle conventions in that file. No FK to `catalog_products` — the rest of the schema does not use
them and this is not the prompt to change that.

### 2.2 Backfill (dry-run first, apply only on approval)

1. For **every** product (all 7,191, not just the 57), insert one row:
   `(item_code, division, is_primary = true)` from the current `catalog_products.division`.
2. For the 57 composites, **split the stored string on `|`**, trim each part, and insert one
   membership row per part. The primary is per Decision 1; the others get `is_primary = false`.
3. Then set `catalog_products.division` for those 57 to the **primary alone** — this is the only
   write to `catalog_products` in this prompt.
4. Assert afterwards:
   - `SELECT count(*) FROM catalog_products WHERE division LIKE '%|%'` → **0**
   - every `catalog_products.item_code` has exactly one `is_primary` row
   - `SELECT count(DISTINCT item_code) FROM product_divisions` = `SELECT count(*) FROM catalog_products`
   - the 57 composites produce **119 membership rows** — 57 primary + 62 non-primary
     (50×2 + 2×2 + 2×2 + 3×3 = 100 + 4 + 4 + 9 = 119)
   - `product_divisions` totals **7,253 rows** — 7,134 single-division products + 119
   - show the before/after per-division counts alongside these assertions

Produce the dry-run report as a table of every affected item code with its old composite value, its
new primary, and its membership rows. **Show it and wait.**

## 3. Item codes — code fix only, no rewrite

### 3.1 First: measure the full collision set (read-only)

```sql
-- Every group of existing codes that would merge under canonical normalisation
SELECT upper(regexp_replace(regexp_replace(btrim(item_code),'\s+','','g'),'\.0$','')) AS canonical,
       count(*)                 AS n,
       array_agg(item_code ORDER BY item_code) AS variants
FROM catalog_products
GROUP BY 1
HAVING count(*) > 1
ORDER BY n DESC, canonical;
```

For every group returned, also report: product names, divisions, categories, whether each has MRP
history, and whether each has matched competitor rows. **This tells us whether they are genuine
duplicate products or two different items whose codes happen to collapse.**

### 3.2 Then: the code fix, with stored codes untouched

- Keep the P057 A.3(a) consolidation: one canonical `normCode` in
  `artifacts/api-server/src/lib/catalog.ts`, `catalogueMatcher.ts`'s aggressive variant renamed
  `matchKey` and confined to fuzzy matching, the duplicates in `import-parse.ts`, `pdfExtractor.ts`
  and `priceHistoryStatus.ts` deleted.
- **`normCode` is used for comparison and lookup only.** No loader changes what it stores.
  Revert/skip the `authoritativeCode` re-point from P057 A.3(a).
- Add a regression test asserting that `TTS-01` and `TTS - 01` are *recognised as the same lookup key*
  while both continue to exist as distinct stored rows. That is the actual current state and the test
  should lock it until §3.3 resolves it.

### 3.3 Duplicate resolution — separate, later, business-led

The `TTS-01` / `TTS - 01` pairs are a **data-quality question, not a normalisation question**: are
they one product entered twice, or two products? Merging them means choosing which MRP history
survives. That is a Preeti-and-team decision with price consequences, and it does not belong in this
prompt. Produce the §3.1 report, hand it over, stop.

### 3.4 Junk rows — flag, do not delete

Three rows in the 262 look like they are not products:

- **`ITEM CODE`** — almost certainly a header row loaded as a product. Report its division, category,
  MRP history and load batch.
- **`Cistern`** — a category name sitting in the item-code column.
- **`EP-Ganesha`** — may be legitimate; report it so someone can confirm.

Report all three with full provenance. **Delete nothing.** Note that `Test` (3 products) has already
disappeared from production since 11 October — confirm with the team that this was intentional and
that those were the 3 codes previously marked "Invalid Input".

### 4.3 Stop it recurring

`artifacts/api-server/src/routes/catalogImportExport.ts:447` stores `norm(row[categoryCol])` where
`norm` is only `String(s ?? "").trim()` — trim, no case handling. That is why both spellings exist.

Add a **canonical-category reuse step** on import, modelled on the competitor-name reuse that already
exists: if an incoming category matches an existing one case-insensitively after trimming, **reuse the
stored spelling** and disclose it in the preview — *"Category 'SWR PIPE' matched existing 'SWR Pipe';
the stored spelling will be used."* Do not silently rewrite, and do not auto-create a second spelling.

### 4.4 Report only — do not act

Two things to surface for a later decision:

- **394 products have a blank or null category** — the second-largest bucket in the whole catalogue.
  Report them by division so the team can see whether it is one workbook or spread across all of them.
- **`category` is being written from `series`.** `authoritativeMrpMaster.ts:442-444` writes the same
  source column into both `category` and `series_range`. That is why the category list has ~400 values,
  200+ of them with a single product, and why they read like model names (`Lavish (Matt Black)`,
  `Orissa Pan 23"`, `Nexa (Matt Khaki)`) rather than categories. It is also why
  `priceFinder.ts:598` labels the field **"Series"** while five other screens label it **"Category"**.

  **This is the root cause of the category dropdown being unusable, and it is a bigger decision than
  this prompt.** Either stop writing `series` into `category` and source a real category, or rename
  the field to Series everywhere and accept there is no category level. Quantify it — how many
  products would have no category at all if the `series` write were removed — and hand it over.

  P057 Part B's searchable dropdown makes a 400-entry list survivable. It does not make it correct.
