## 2. Test this hypothesis first, before diagnosing anything

**Hypothesis: the history controls are disabled because an unresolved pending batch exists.**

A loader that is strictly all-or-nothing has a coherent reason to disable undo on batch 90 while
batch 91 is pending — undoing 90 would leave 91's staged change set stale and no longer verifiable
against the catalogue.

Test it in this order:

1. Confirm batch 91 is a **zero-change** batch (it should be; the re-preview reported 0).
2. **Discard / cancel batch 91** through the app's own path for abandoning a pending preview. Not by
   direct SQL.
3. Re-check the history view: can you now open batch 90's details, and is an Undo control visible?

| Result | Conclusion |
|---|---|
| Controls become available | **That was the cause.** Not a defect — document the behaviour and move on. |
| Still disabled | Go to §3. |

If other orphaned pending batches from §1 are present, discard those too, and say whether the
controls changed after each or only once all were cleared.

## 7. Build-info — the typecheck decision

`GET /api/_build` at `7c27c16` is sound, and one detail in it is exactly right: **it fails the build
when `BUILD_COMMIT_SHA` / `BUILD_BRANCH` are absent rather than emitting a guessed identity.** An
endpoint that guesses would have been worse than no endpoint — it would have answered P066 Step 1
with a plausible lie.

It is blocked by pre-existing typing errors in unrelated animation/film files. Two options, your call:

1. **Scope the gate** — publish on the API package typecheck, which passes, and track the unrelated
   errors separately. Defensible: the failing package shares no code with this change.
2. **Fix the unrelated errors first** — cleaner, but it makes a three-line observability endpoint wait
   on debt it did not create.

I lean to (1), with the pre-existing errors logged as their own item. Do not disable or loosen the
workspace typecheck to get there.
