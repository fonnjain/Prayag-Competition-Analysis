## Part A — Division / Category / Item-code mapping is wrong in places

### A.1 The evidence

The Price Finder "Browse the catalogue" screen currently lists these as divisions:

| Division as shown | Products |
|---|---|
| CP (QUAA / FERN) | 161 |
| CP Fittings / Faucets | 1040 |
| **CP Fittings / Faucets \| Ceramic Sanitaryware** | **2** |
| **CP Fittings / Faucets \| PTMT & Plastic Fittings** | **2** |
| **CP Fittings / Faucets \| PTMT & Plastic Fittings \| Pipes & Fittings** | **3** |
| Ceramic Sanitaryware | 217 |
| **Ceramic Sanitaryware \| PTMT & Plastic Fittings** | **50** |
| Hardware | 285 |
| PTMT & Plastic Fittings | 2071 |
| Pipes & Fittings | 2288 |
| **Test** | **3** |

Four of those are **pipe-joined composites**, not divisions. They hold **57 products between them**,
and those 57 products are **invisible** when a user picks the real division — the 50 products under
`Ceramic Sanitaryware | PTMT & Plastic Fittings` do not appear under `Ceramic Sanitaryware` (217)
and do not appear under `PTMT & Plastic Fittings` (2071). A user browsing a division is silently
shown an incomplete catalogue. There is also a junk `Test` division with 3 products.

### A.3 Step 2 — code fixes that are unambiguous (do these now, they are safe)

These are real bugs regardless of what the team decides about the 57 products.

**(a) One `normCode`, not four.** There are four divergent implementations of the same item-code
normaliser, exported under the same name from different modules:

| File | Behaviour on `WMP-188 (A)` |
|---|---|
| `artifacts/api-server/src/lib/catalog.ts:90` | `WMP-188(A)` |
| `artifacts/api-server/src/lib/catalogueMatcher.ts:59` | `WMP188` |
| `artifacts/api-server/src/lib/import-parse.ts:26` | `WMP-188(A)` |
| `artifacts/api-server/src/lib/pdfExtractor.ts:140` | `WMP-188(A)` |

plus `artifacts/api-server/src/lib/priceHistoryStatus.ts:16` (`normalizeCode`, byte-identical to
`catalog.ts`) and `artifacts/api-server/src/lib/authoritativeMrpMaster.ts:87` (`authoritativeCode`,
which does **not** strip internal whitespace).

Do this:
- Keep `catalog.ts:90` `normCode` as the single canonical implementation and export it.
- `catalogueMatcher.ts` genuinely needs its more aggressive form for *fuzzy matching* — **rename it
  `matchKey`** and leave its behaviour and its tests (`catalogueMatcher.test.ts:64-79`) alone. It must
  never be used as a storage or join key.
- Delete `import-parse.ts:26`, `pdfExtractor.ts:140`, `priceHistoryStatus.ts:16` and re-point them at
  the canonical `normCode`.
- Re-point `authoritativeCode` at the canonical `normCode`. **Note this changes what the authoritative
  loader writes** — call that out explicitly in your summary; do not backfill existing rows here.
- Add a unit test asserting all storage/join call sites agree on a fixture set that includes
  `"WMP-188 (A)"`, `"12345.0"`, `" u21 "`, `"RPS-2285"`.

**(b) The Price Finder division filter is dead for 4 of the 6 divisions.**
`artifacts/api-server/src/routes/priceFinder.ts` builds the search needle with `normalise()`
(line ~294) which keeps `/ & ( )`, then matches it against a SQL column stripped of *all*
non-alphanumerics (line ~428-434):

```ts
// needle:  "cpfittings/faucets"     ← keeps the slash
// haystack: regexp_replace(lower(...), '[^a-z0-9]', '', 'g')  → "cpfittingsfaucets"
```

So the branch never matches for `CP Fittings / Faucets`, `CP (QUAA / FERN)`,
`PTMT & Plastic Fittings` or `Pipes & Fittings`. **Fix:** make `normalise()` use the same
`[^a-z0-9]` class as the SQL, and add a test that each of the six live division strings round-trips.

**(c) `/analysis/filters` returns a different option set from `/catalog/filters`.**
In `artifacts/api-server/src/routes/analysis.ts` (~line 396) the distinct division/category query has
**no `is_active` / `discontinued_from` predicate**, while `catalog.ts:234-261` has one. The Analysis
dashboard therefore offers divisions and categories that only exist on inactive or discontinued
products. Add the same predicate.

**(d) Category is not scoped by the selected division on the Analysis dashboard.**
`/analysis/filters` returns `categories: string[]` with the division dropped (~line 420-426), and
`artifacts/prayag-analysis/src/pages/dashboard.tsx:309` renders it unscoped. Picking Division A plus a
Category that only exists in Division B silently returns zero rows.
**Fix:** return `{ category, division }[]` from `/analysis/filters`, scope the Category select by the
selected division, and reset `category` to `"all"` when `division` changes — mirror exactly what
`artifacts/prayag-product-db/src/pages/catalog.tsx:185-191` and `:230-233` already do correctly.

**(e) Two spellings of the same sentinel.** `priceFinder.ts` emits `'Uncategorised'` (en-GB) and
`comparison.ts:785` emits `'Uncategorized'` (en-US). Worse, `/price-finder/browse` round-trips
`'Uncategorised'` as a division value but `/catalog/products` does a literal
`eq(division, 'Uncategorised')` which matches no row.
**Fix:** stop sending a sentinel from the API. Return `null` and render the label
`"Uncategorised"` in the UI only. Where the sentinel is used as a round-trip filter value, use an
explicit `?division=__none__` flag that the handler translates to `IS NULL`.

**(f) `QUAA & FERN` vs `CP (QUAA / FERN)`.** `FILENAME_DIVISION_MAP`
(`artifacts/api-server/src/routes/catalogImportExport.ts:817-831`) maps `/quaa|fern/i` to
`"QUAA & FERN"`, but the live division value is `"CP (QUAA / FERN)"` and `OFFICIAL_MRP_SOURCES`
(`artifacts/api-server/src/lib/mrpProvenance.ts:37-76`) also uses `"CP (QUAA / FERN)"`.
`FILENAME_DIVISION_MAP` also has **no `/hardware/i` pattern**, so a Hardware workbook loaded through
that path lands with `division = null`.
**Fix:** export the six canonical division strings from one module, derive `FILENAME_DIVISION_MAP`
from it, add the Hardware pattern, and make the `anomalyReasons` regex at
`catalogImportExport.ts:707` use the same source instead of its own fourth spelling set.

**(g) Delete the stale merge artefacts** at the repo root: `comparison.ts.ours`, `comparison.ts.theirs`,
`comparison.ts.common`. They contain live-looking category logic and will mislead the next person
grepping for it. Confirm nothing imports them first.

## Part B — Dropdowns: no scroll, and no search

### B.1 What is actually wrong

The complaint splits in two, and only one half is what it sounds like.

**The Radix `Select` dropdowns do already scroll.** `src/components/ui/select.tsx` (duplicated in all
five apps) sets `max-h-[--radix-select-content-available-height] … overflow-y-auto` on `SelectContent`.
The real problems are:

1. **`max-h` is the whole available viewport height.** On a large monitor a long list renders a panel
   the full height of the window with every option mounted — Radix Select does not virtualise. With
   4,500+ SKUs that is a hard freeze.
2. **`PopoverContent` (`src/components/ui/popover.tsx:22`) has `w-72` and no `max-h`, no `overflow`.**
   Anything list-shaped dropped into it renders unbounded.
3. **Price Finder's division and category pickers are not dropdowns at all.** In
   `artifacts/prayag-price-finder/src/pages/home.tsx`:
   - the division picker (~line 1004) is a `grid gap-1.5 sm:grid-cols-2` of buttons with **no height
     bound and no scroll**;
   - the category picker (~line 1029) is a horizontal pill row with
     `overflow-x-auto … [scrollbar-width:none] [&::-webkit-scrollbar]:hidden` — it scrolls sideways
     **with the scrollbar deliberately hidden**, so most categories are off-screen with only a faint
     gradient hint that they exist. **This is almost certainly the "dropdown does not have scroll"
     report.**
   - the product list (~line 1076) has no vertical bound either; it is only survivable because the API
     clamps `limit` to 300 (`priceFinder.ts:637`).
4. **Not one dropdown in the entire repo has a text-search input.**

## Part C — Competitors must be scoped to the selection

### C.1 What is wrong

The Price Finder comparison page shows a **hardcoded row of brand checkboxes** — currently
Sparsh Pearl, Ashirvad, Prince, Vectus — on every product, whether or not that product has a price
from that brand. A user comparing a PVC Connection sees four brands and gets one column of data. Vectus
in particular is supported in the app but **has no price data at all**.

The brand list is hardcoded in **two files that must be edited in lockstep**:

- `artifacts/prayag-price-finder/src/lib/priceFinderRouteState.ts:6`
  `export const PRICE_FINDER_COMPETITORS = [...] as const;`
- `artifacts/api-server/src/routes/priceFinder.ts:17`
  a second, separate literal copy, enforced as a 400 at ~`:1041` and ~`:1074`.

Every other competitor list in the app is the **global** distinct `competitor_prices.competitor`
set, unscoped by division, category or product:

| Route | File |
|---|---|
| `GET /catalog/comparison/filters` | `comparison.ts:1512` — no `.where()`; `?competitor=` narrows only `periods` |
| `GET /analysis/filters` | `analysis.ts:387` — handler signature is `(_req, res)`, it cannot read a query param at all |
| `GET /catalog/competitor-brands` | `catalogImportExport.ts:2160` — `(_req, res)`, no `.where()` |
| `GET /analysis/discount-settings` | `analysis.ts:914` → `getDiscounts()` at `:293` |

The one thing that already does it right is `GET /price-finder/product/:itemCode`
(`priceFinder.ts:806`), whose brands subquery at `:930-937` is exactly the shape we want:

```sql
SELECT DISTINCT cp.competitor
FROM competitor_prices cp
WHERE cp.matched_prayag_code = $1
  AND cp.match_status = 'matched'
  AND cp.price IS NOT NULL
  AND cp.effective_date <= CURRENT_DATE
```

### C.2 The fix

**1. Delete both hardcoded arrays.** Drive the competitor set from data.

**2. Add one new endpoint** — `GET /price-finder/competitors`:

```
GET /price-finder/competitors
  ?itemCode=U76                 (repeatable — scope to these products)
  |  ?division=…&category=…     (scope to a classification)
  &asOf=YYYY-MM-DD              (optional, defaults to today)
```

Returns only competitors that actually have a usable current price in scope:

```jsonc
{
  "asOfDate": "2026-10-16",
  "scope": { "itemCodes": ["U76"], "division": null, "category": null },
  "competitors": [
    { "competitor": "Sparsh Pearl", "pricedProducts": 1, "coveragePct": 100 }
  ],
  "productsInScope": 1,
  "productsWithNoCompetitorPrice": 0
}
```

Query shape — note the join must go through `catalog_products` because `competitor_prices` has **no
division column**:

```sql
SELECT cp.competitor,
       count(DISTINCT cp.matched_prayag_code) AS priced_products
FROM competitor_prices cp
JOIN catalog_products p ON p.item_code = cp.matched_prayag_code
WHERE cp.match_status = 'matched'
  AND cp.price IS NOT NULL
  AND cp.effective_date <= $asOf
  AND ( $itemCodes::text[] IS NULL OR cp.matched_prayag_code = ANY($itemCodes) )
  AND ( $division IS NULL OR p.division  = $division )
  AND ( $category IS NULL OR p.category  = $category )
GROUP BY cp.competitor
ORDER BY priced_products DESC, cp.competitor ASC;
```

Use `normCode` (Part A.3a) on both sides of the join key once that work is merged. Existing indexes
`competitor_prices_matched_code_idx`, `competitor_prices_competitor_idx` and
`competitor_prices_current_idx` cover this; add a `(category, competitor)` composite only if the
explain plan asks for it.

**3. Wire the comparison page to it.**
`artifacts/prayag-price-finder/src/pages/comparison.tsx:107-119` renders the checkbox row from
`PRICE_FINDER_COMPETITORS`. Render it from `GET /price-finder/competitors` keyed on the current
selection instead.

- A brand with **zero** priced products in scope is **not rendered**. (Not greyed out — not rendered.
  That is what was asked for.)
- Each checkbox shows the coverage count, e.g. `Brand A (12)`, so the user can see depth before
  selecting.
- If the scope yields **no** competitors at all, replace the row with
  *"No competitor prices recorded for this selection."* — do not show an empty checkbox strip.
- Preserve the current URL-param round-trip, but validate the param against the **fetched** list
  rather than a hardcoded union. An unknown or now-uncovered brand in the URL is dropped silently
  rather than 400-ing the page.

**4. Apply the same scoping to the division/category dropdowns on the Analysis dashboard and the
Product DB comparison page.** `/catalog/comparison/filters` and `/analysis/filters` should accept
optional `division`, `category` and `itemCode` params and narrow `competitors` accordingly.
`analysis.ts:387` must stop using `(_req, res)`.

**5. Do not change** what counts as a valid comparison row. Reuse the existing predicates
(`match_status = 'matched'`, `price IS NOT NULL`, `effective_date <= asOf`,
`isAvailableComparisonRow`). This prompt changes *which brands are offered*, never *which prices are
comparable*.

### C.3 Acceptance

- Selecting Division = Ceramic Sanitaryware shows only brands with sanitaryware prices.

- Every brand shown has at least one real price behind it, and the count next to it is correct.
