# PART B — `PMN032404` is a product-identity dispute and carries no flag

```
code      PMN032404
price     Rs 187.50   in BOTH sources
workbook  "Multi Floor Trap with Jali"
PDF p.24  "WITHOUT JALI"
```

Classifying it as a description difference rather than a price disagreement is technically right, and **that is exactly what makes it dangerous**. With-jali and without-jali are different products that do not share a price in reality. One of the two sources has that price against the wrong variant — so Prayag's with-jali product may be being compared against Apollo's without-jali price.

**This is the same-price misalignment that price agreement alone cannot exclude.** The check found one. It has no badge. Only `PMN03122V` does.

**B.1** Flag `PMN032404` as a **product-identity dispute** — a distinct kind from a price dispute. Do not change the price, do not choose a variant, do not remove the row.

**B.2** The **nine indeterminate** codes get a visible **not verified** marker — not asserted as disputes, but not presented as confirmed either:

```
CM02350W0V · CM0235010V · PM0389042V · PM03890403 · PM03890404
PM03890402 · PPRMB021225MM0V · PPRMB021720MM0V · PPRMB021725MM0V
```

**B.3** Re-run the description comparison after Part A and report whether any of the **246 wording-only** differences reclassifies as a likely misalignment once sizes are available. A size disagreement alongside a wording difference is a much stronger signal than either alone.

Report the new counts: exact, wording-only, likely misalignment, indeterminate.

# PART C — Record what the new key does not solve

The identity is `v2|<sheet class>|<Prayag code>|<size>`. It is anchored on the **Prayag** item code.

In a workbook that works — every row carries the Prayag code beside the Apollo one. **The PDF does not.** So the identity cannot be derived from Apollo's own document, which is why 248 of the 275 held rows read *"existing Prayag target, but no matching PDF pipe identity found."*

**If Apollo's next price list arrives as a PDF, as this one did, the 272 pipe rows still cannot be matched from it.** Somebody rebuilds the pairing workbook by hand.

That is an acceptable limitation. It is not acceptable for it to be a surprise.

**C.1** Record it where whoever runs the next Apollo load will see it — in the import screen when an Apollo PDF is selected, not only in a report. State plainly: pipe rows cannot be matched from a PDF and require the pairing workbook.

**C.2** Report how many of the 272 pipe rows would match from a PDF today. If the answer is zero, say zero.

**C.3** **Propose, do not build:** what would let a PDF match a pipe row directly? Apollo's own description and size are on the page. If a second identity — supplier-side, derived from Apollo's text — could carry that, say what it would take and what it would risk. This is a design note for later, not work for now.
