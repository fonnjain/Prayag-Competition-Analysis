# P031 — COMPETITION — Why are past price periods not showing?

> **P031** · app: **COMPETITION** (`prayag-price.com`)
> **READ-ONLY. Change nothing.** No commits. No data changes. No count adjustments. No reloads.
> Quote `P031` when reporting back.

Past periods are not displaying correctly after a price revision upload. This prompt establishes whether the rows are missing from the database or present but not being shown. Those are different problems with different fixes, and guessing between them is how rows get deleted.

---

## 1. The fork — answer this first

```
mrp_price_history row count      last reported as 14,102
```

The source rebuild that built this history holds **12,750 rows across 16 distinct periods**.

- If the table holds **~14,000 rows**, the history is there and something in the **display** is filtering it. Go to §3.
- If it holds **~6,100 rows** — roughly one per product — then only the current-price snapshot was ever loaded and the history is genuinely absent. Go to §4.

Report the count first. Everything else follows from it.

The history came from the separate all-periods rebuild.

## 3. If the rows are present — find the filter

Report each of these:

1. **Every distinct `effective_date` in `mrp_price_history`, with its row count.** Diff against the 16 above. Name any period present in one and not the other.
2. **How the application builds its list of periods.** Read from `SELECT DISTINCT effective_date`, or from a periods table, a config entry, a constant, or a date range? **Quote the code.**
3. Whether any query filters by `is_current`, a date floor, a "live periods" list, or a row limit. `is_current` was retired as a source of truth — report anywhere it is still read.
4. Whether the product detail view, the price history table and the Historical MRP view each derive periods independently or share one source.

**A fixed or configured period list is the most likely cause.** The application has been described as holding "6 live periods", and the source has 16. If the six are hardcoded or held in config, the other ten are invisible however many rows exist — and the row count will look healthy while the screen looks empty.

This is the same class of fault as the recent 11-of-13 worksheet read: something conformed to an expected list instead of reading what was actually there.

## 4. If the rows are absent — find what was loaded

2. Which batch carried multi-period history, if any.
3. Whether any batch loaded 12,750 rows or close to it.
4. Whether a later batch replaced rather than added to earlier rows.

**Do not reload anything.** Establish what happened first.
