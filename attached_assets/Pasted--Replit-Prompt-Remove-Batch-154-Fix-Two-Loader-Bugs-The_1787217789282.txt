## Part A — Remove batch 154 now


### Why deleting is correct here

This is not tidying a count. These rows are provably invalid on three independent grounds:

1. Their effective date is the **load date**, not any period in the workbook. The file's columns are `5th Mar, 2026` and `01st Sep, 2026`. There is no 20 August period.
2. They came from a file **already loaded as batch 2** — same SHA-256, `5da96e39cac40ede…`.
3. They are displacing correct prices in the running application.

The diagnosis is complete, so nothing is lost by removing them.

## Part B — The duplicate guard checks only the latest batch

Your diagnosis: the guard compares the incoming hash against the **most recent** batch for the source. Batch 113 (the March file) sat between batch 2 and this reload, so the matching September checksum in batch 2 was never reached.

Compare the incoming SHA-256 against **every** batch for that source, not just the latest. Report all matches, with batch id, filename and load date, so the user sees the full history rather than one prior load.

The March file was itself a mistake, but the guard must not depend on nobody ever loading the wrong file. Anything that only inspects the most recent record has this failure mode by construction.

## Part C — Effective dates must come from the workbook, never the load date

A file whose only periods are `5th Mar, 2026` and `01st Sep, 2026` produced 1,828 rows dated `2026-08-20`. The loader used the load date as the effective date.

**This is the more dangerous of the two bugs.** The guard failure allowed a duplicate load; this one means *any* load can silently create a "today" period that outranks every real revision. It would have corrupted prices even with a legitimately new file.

Find where the effective date is assigned and make it read from the column header. Then add a hard rule:

> A price row's effective date must correspond to a dated column in the source workbook. If a period cannot be resolved from the sheet, reject the row and report it. Never substitute the load date, today's date, or any default.

`load_date` and `effective_date` answer different questions and must never fall back to one another — the same distinction as `downloaded_at` versus `loaded_at` in the provenance work.

Report which periods this loader now resolves for the PTMT workbook. Expected: **2026-03-05** and **2026-09-01**, nothing else.
