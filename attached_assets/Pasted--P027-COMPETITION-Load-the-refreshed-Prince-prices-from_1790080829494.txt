## 3. Code normalisation is mandatory

**74 of the 813 rows will fail to match without it.** The Competitor Master writes codes with spaces where the catalogue has none:

```
'PU-1 T'   ->  'PU-1T'
'PU-6 TS'  ->  'PU-6TS'
'PW 71'    ->  'PW71'
'PW 54'    ->  'PW54'
```

This is the same class of problem as P008, where `324-K` and `324K` were the same product and eight codes worth Rs 54.2 lakh were being lost.

Apply the same normalisation the resolver already uses — strip everything that is not a letter or a digit, compare case-insensitively. If this import path does not already normalise, **that is the code change this prompt requires**, and it must be made before the load rather than worked around by editing the spreadsheet.

Report how many rows matched exactly, how many matched only after normalising, and how many did not match at all. A normalised match must be reported as such, never silently treated as exact.

## 4. Rows that must be rejected, not skipped

A rejected row is named in the report. A skipped row disappears. These must be rejected:

**`SIM200032` appears twice with different prices.** AGRI PIPE: `A-86B` at 1265 and `A-86A` at 759. One Prince SKU cannot carry two prices — one of those rows has the wrong code on it. Reject **both** rows and name them. Do not pick one. Do not average. Do not take the last one read.

**`PMR-5` carries a Prince price of `0.00` with no Prince code and no Prayag price.** Reject it. Zero is not a price. Missing data is not zero — a zero here would show Prince undercutting Prayag by 100% on a casing pipe.

## 7. Rules that do not bend

1. **A competitor upload must never create a Prayag product.** Not in this load, not as a convenience, not behind a checkbox. Any row whose Prayag code cannot be resolved is held and listed for a human.
2. **Do not read the Prayag price column.** It is dated 10 August and is known stale — its Casing Pipe values are the February prices, about 10% below what the catalogue now holds. Reading it would silently overwrite correct prices with old ones. This load takes the Prince columns only.
3. **The effective date is `2026-03-01`, from the Prince column header.** It is not the upload date. Batch 154 wrote 1,828 rows dated the day they were loaded and overrode correct March prices; if an effective date here falls back to today, stop and report it.
4. **Preview, then Apply.** Nothing is written until a human applies it.
5. **Provenance.** `mrp_load_batches` row with the SHA-256, row count and actor; `load_batch_id` on every competitor price row written.
6. **No direct SQL against production.** The load goes through the application's own validated path.
