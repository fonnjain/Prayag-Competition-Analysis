# P033 — COMPETITION — Restate 90 PPR pipe prices from per-metre to per-pipe

> **P033** · app: **COMPETITION** (`prayag-price.com`)
> **THIS PROMPT CHANGES DATA.**
> Quote `P033` when reporting back.
> **Run this before, or in the same session as, P028's PPR load.** See §7.

The 90 PPR pipe prices in this application are **per metre**. The product is a **3-metre pipe**. The MRP Prayag publishes is the per-pipe figure.

Prayag has confirmed the cause: the MRP originally supplied was for one metre, while the pipe length is three metres.

**This is a unit restatement. It is not a price change.** Not one product changes price in real terms, and nothing in this prompt may record it as an increase.

---

## 1. The evidence

Every one of the 90 codes in the correction file is exactly **3×** the stored value:

```
code       app (per metre)   file (per 3 MTR pipe)
P10A03               108                    324
P10A05               268                    804
P10A10             1,722                  5,166
P10G02                68                    204
```

72 of 90 are exactly 3×. The remaining 18 differ by **exactly ±1 rupee**, because the app stores a *rounded* per-metre value and multiplying by three cannot recover the lost rupee — `P10A02` is ₹235 per pipe, ₹78.33 per metre, stored as ₹78, and 78 × 3 = 234.

**Every other pipe category is already per-pipe.** PPR is the only one that is not:

```
Casing Pipe   PMC-1    app 682     per-metre 227.33    per-pipe 682     correct
UGD Pipe      U-11C    app 2,987   per-metre 497.83    per-pipe 2,987   correct
PPR Pipe      P20G02   app 108     per-metre 108       per-pipe 324     WRONG
```

The competitor master's own PPR section header reads *"Green Triple Layer … 3 Mtr"*, and the 155 name changes append `" Pipe (3 MTR)"` to these same 90 products. Name and unit are one correction arriving in two files.

## 2. Use the file's values. Never compute 3×.

**File:** `Master - MRP PPR.xlsx`
**SHA-256** `f27fa5f40e9428fe8d953ad13803d5d46d667f4f399ff1ba46e63449cb603288`
Sheet1, 90 rows, columns: `Cat No. · Division · Series / Range · Product Name · MRP w.e.f. 10 Aug 2026 · Previous MRP 01 Feb 2026`

Record the hash before reading a row.

**Do not multiply the stored price by three.** Eighteen codes would land a rupee out. The file carries the true per-pipe values; take them.

Verify before writing: for each code, the stored value × 3 should be within ±1 of the file value. **If any code is further out than ±1, stop and report it** — that would be a real price change hiding inside a unit correction, and it must not pass silently.

## 3. Restate in place. Do not add a period.

```
correct       the existing rows, at their existing effective dates
never         insert a new row, a new period, or a new effective date
```

If this loads as a revision, every PPR product reads as a **200% increase**. That flows into margins, the MRP generator, every saved scenario, the historical comparison, and the Sales application. A unit restatement recorded as a price rise is worse than no correction at all.

Each corrected row carries an audit note saying **unit restatement, per metre to per 3-metre pipe — not a price change**, so that anyone reading the history later sees why the number moved.
