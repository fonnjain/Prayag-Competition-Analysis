# PART B — The test suite must not be able to reach production

This is the real finding of Step 4, and it outranks the teardown fix.

The integration test inserts into `catalog_products` and nothing stops it pointing at production. Production holds none today — but "none today" and "cannot" are different answers, and Step 4 returned *could*.

A leaked fixture in development is untidy. The same test run with production credentials in the environment writes junk into the live catalogue, and it arrives looking like a real product.

## B1. Add a database-target guard

It runs at **suite setup, before any fixture is inserted**, and it must:

- read the target database identity **from PostgreSQL itself** — `SELECT current_database()` — never from an environment variable, a connection string, or `NODE_ENV`
- refuse to run unless that name matches an explicit development or test allowlist
- **fail the whole suite loudly** on a non-match, before `beforeAll` executes
- have **no override** — no force flag, no environment variable that disables it

The sibling application already uses this pattern: it derives its data source from `current_database()` and raises rather than inferring provenance from a URL. Same reasoning, applied one layer earlier.

## B2. Prove it

Point the suite at a database name outside the allowlist and confirm it refuses **before inserting anything**. Report the error.

## B3. Sweep the rest of the suite

The integration test is one file. The question is how many others write to production-shaped tables.

List **every** test that inserts, updates or deletes in `catalog_products`, `mrp_price_history`, `mrp_load_batches`, `competitor_mapping`, or any other live table, and confirm each is covered by the guard.

**A guard on one file is not a guard.**
