# PART 4 — The decisions must survive the next load

**The competitor master still contains every one of these rows.** Nothing has been removed at source.

So unless these decisions are recorded as persistent state, the next load of that file will:

- hit the `SIM200032` conflict again and re-reject it, with nobody knowing it was already decided
- **re-create the `SIM100150` → `A-464` mapping that was just deleted**
- re-flag `SIM103500` and `SIM103501` as anomalies needing review

That last one is noise. The middle one silently undoes Part 2.

**Build the exclusions as durable records that the loader consults**, keyed on **the Prince code and the Prayag code together** — never on a row number. Row 20 and row 51 move the moment Prayag edits the workbook, and a decision keyed to a row number will then apply to the wrong product.

On a future load, a mapping on the exclusion list is **skipped and reported as "excluded by decision"**, never silently, and never re-created.

Report how you stored this and where the loader reads it.

**Also report:** whether these rows should be removed from the competitor master at source. That is Prayag's call, not yours — but a decision recorded in two places that can disagree is worth naming now rather than discovering later.
