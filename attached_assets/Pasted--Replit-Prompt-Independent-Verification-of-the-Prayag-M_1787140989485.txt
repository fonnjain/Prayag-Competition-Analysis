# Replit Prompt — Independent Verification of the Prayag MRP Work

## 1. What this is, and what it is not

Several rounds of MRP work are now committed: the full history rebuild, the discontinuation rule, the phantom-row deletions, and source provenance. This task **verifies** that work. It does not extend it.

**This is a read-only exercise.** Do not fix anything you find. Do not adjust a figure to match an expectation. Do not update a test so it passes. If a check fails, record what the database actually contains and move on to the next check. A verification pass that quietly repairs its own failures verifies nothing.

Two rules for the report:

- **Every figure must be read from the database at the time of writing**, not restated from this prompt, not carried over from an earlier report, and not inferred from code.
- **State each result as pass or fail against the stated expectation.** "Looks correct" is not a result. If a number differs by one, that is a fail and should be reported as one.

The expected values below were computed independently from the six official workbooks. Where the database disagrees, the disagreement is the finding.

## 5. The rule, not just the rows

Correcting 61 rows without correcting the rule leaves the defect in place. Verify the rule itself.

`deriveConfirmedDiscontinuations()` in `lib/discontinuationPolicy.ts` groups by code and requires every occurrence to be removed. Confirm by behaviour rather than by reading it:

1. **Idempotency.** Re-run the loader against the same six workbooks. Afterwards: row count still 12,750, discontinued count still 98, and none of the 61 re-marked. Report all three.
2. **Unit behaviour.** Feed `deriveConfirmedDiscontinuations` a code with one removed row and one live row for the same period. It must return nothing. Feed it a code whose every row is removed. It must return that code with the earliest withdrawal date.
3. **Price and marker together.** A code carrying both a withdrawal marker and a price for the same period must keep the price in history and still be withdrawn from that date. `616-D` is the case in the data; confirm it holds as a rule and not as a one-off correction.

## 8. The gap calculation

Still outstanding from the previous round, and the one thing a dataset-wide median will not settle. Trace a single row: Prayag `134-V` ↔ Sparsh Pearl `RPS-2285`.

| Value | Amount |
|---|---:|
| Prayag MRP w.e.f. 05 Mar 2026 | 1,262.35 |
| Prayag MRP w.e.f. 01 Sep 2026 | 1,364.00 |
| Sparsh Pearl Vol 6.2 MRP | 1,388.00 |

Under the documented convention — positive means Prayag is cheaper — today's gap is `(1388.00 − 1262.35) ÷ 1262.35 = +9.95%`.

Report three things and change nothing:

1. What the dashboard displays as this row's gap today.
2. The exact two numbers the code divides, and the table each comes from.
3. Whether the Prayag side is read live from `mrp_price_history` or from the stored `competitor_prices.prayag_mrp_at_compare` snapshot.

Point 3 decides it. The schema comment on `prayag_mrp_at_compare` says the gap is computed only against that persisted value; the project notes say analysis is live-computed and gaps are never stored. Both cannot be true for the same view. If the dashboard reads a pre-rebuild snapshot, it shows old prices no matter what the history now contains.
