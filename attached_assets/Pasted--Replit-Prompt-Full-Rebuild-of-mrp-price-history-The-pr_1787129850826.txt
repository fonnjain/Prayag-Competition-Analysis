### The 2026-04-20 period is actively wrong and must go

Those 930 rows are the **01 Sep 2026 revision under the wrong date**. Each value is the 05 Mar price multiplied by exactly 1.08, before the source rounded it:

| Code | 05 Mar | × 1.08 | DB @ 20 Apr | Official 01 Sep |
|---|---:|---:|---:|---:|
| `123-Q` | 375.5232 | 405.5651 | 405.57 | 406.00 |
| `121-B` | 226.00 | 244.08 | 244.08 | 244.00 |
| `148-LS` | 385.56 | 416.40 | 416.40 | 416.00 |

It covers only about half of PTMT, so the catalogue contradicts itself today. In the live Price Finder, `148-LS` (Erosa) shows ₹416.40 while `148-LSB` (Erosa Blue) shows ₹410.00 — the plain variant appearing dearer than the coloured one, when the official file has them at 385.56 and 410.00. Roughly 930 PTMT products are quoting September prices four months early.

The other three unsourced dates are old periods carrying no current price, so they are a labelling problem rather than a live pricing one — but there is no reason to keep them once the rebuild has a properly dated history.

## 2. Input file

`Prayag_MRP_AllPeriods_Rebuild.xlsx`

| Sheet | Rows | Use |
|---|---:|---|
| `mrp_price_history` | 12,768 | one row per `item_code` × `effective_date` — this is the load |
| `catalog_products` | 6,303 | code, division, name, period count, `discontinued_from` |
| `discontinued` | 159 | codes marked `REMOVED` in the source, with the date they stop |
| `conflicts_to_resolve` | 79 | same code priced twice in one period — needs a human decision |
| `summary` | — | counts per period and per division |

### How it was built

- The six official workbooks only. Nothing else was consulted.
- Every column headed `box`, `pcs`, `packing`, `qty`, `coupon`, `diff`, `%age`, `weight`, `erp`, `cost`, `purchase` or `kg` is rejected as a price. This is the guard the packing-quantity incident produced; do not weaken it.
- Each code column is paired only with the price columns in **its own block**, up to the next code column. Wide multi-block sheets such as `PE-AL-PE FITTINGS-2` and `PPR PIPE` would otherwise pull prices from a neighbouring product.
- **The `SINK` sheet has a dedicated handler.** Column `L` decides the layout: when populated the row is a Gloss/Matt block taking `I`/`J` for 05 Mar and `L`/`M` for 01 Sep, and `H`/`K` are **status columns, not prices**. That single adjacency is where the ₹0.05 and ₹0.06 sink prices came from.
- Where `MASTER` and a per-range sheet disagree, `MASTER` wins. Per-range sheets supply only codes `MASTER` does not carry — which is how the 264 Without-Brass items such as `C121` (₹36) and `U121` (₹32.90) are picked up.
- Undated `OLD MRP` / `NEW MRP` columns are dated from sibling sheets in the same workbook that do carry explicit dates. For example the Pipes & Fittings `MASTER` columns are undated, but `C Fittings` carries `MRP as on 1st May, 2024` and `MRP as on 1st Feb, 2026`, so those are the two periods.

Twenty ground-truth values were checked against the source and all twenty match, including `U21` = 78 @ 2026-02-01, `C854` = 44.40 @ 2026-02-01, `121-B` = 226 → 244, `911-D` = 3,240 → 3,490 and `BD-40` = 3,680 → 3,990.

## 3. What to do

### 3.1 Back up first

Copy the whole of `mrp_price_history` to a timestamped backup table before touching anything, and report its row count. Do not proceed if the backup did not write.

### 3.2 Replace

Delete every row of `mrp_price_history` and load the `mrp_price_history` sheet in full. `catalog_products` is **not** deleted — competitor mappings reference it by `item_code`, and deleting underneath them would break the 150 verified Sparsh rows. Upsert products by `item_code` instead: update name, division and `discontinued_from`; insert codes that are new; and for codes present in the database but absent from the file, set `is_active = false` and report them rather than deleting.

`discontinued_from` comes from the `discontinued` sheet. If the column does not exist yet, add it to `lib/db/src/schema/catalog.ts` as a nullable `date` and run `pnpm --filter @workspace/db run push`.

### 3.3 Do not load the conflicts blind

The 79 rows in `conflicts_to_resolve` are codes priced twice in the same period — nearly all are brass/black or finish variants sharing one item code in the source. The file uses the leftmost column's value deterministically. Load that value, but **flag every one of these codes** in the UI as having unresolved variant pricing so the user can settle them later. Do not silently present them as clean.

### 3.4 Then recompute

Run `recomputeCurrentFlags()` after loading. Remember that `is_current` is a convenience only — the current price must still resolve by `effective_date <= CURRENT_DATE` at query time, so PTMT's 01 Sep revision takes effect on its own with no re-import.
