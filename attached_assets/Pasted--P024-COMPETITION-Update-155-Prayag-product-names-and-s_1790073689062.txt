## A3. What must not change — this is most of the job

Nothing in this batch is a price change and nothing in it is a mapping change.

1. **No price is written.** Not one row in `mrp_price_history`. No new period, no new effective date, no re-rounding. The `mrp_unchanged` column is in the file so you can assert this, not so you can load it.
2. **No competitor mapping changes.** Not one row in `competitor_prices`, and no row moves into or out of Needs Review.
3. **No division, series, category or size changes.** The file repeats division and series only so they can be checked; they are identical to what is stored.
4. **No product is created and none is deactivated.**
5. **No discontinued product is touched.**

### The mapping risk, stated plainly

If any matching, scoring or Needs-Review logic anywhere in this application reads `product_name`, then renaming 155 products can silently re-shuffle competitor matches — and it will do so quietly, because nobody is watching the mapping table during a rename.

So, as part of this job:

```
before the update:
    snapshot every competitor_prices row for the 155 codes
    snapshot the full Needs Review queue (count and membership)

after the update:
    take the same two snapshots
    diff them
```

**The diff must be empty.** If it is not empty, roll back and report — do not accept a changed mapping as a side effect of a rename. Report which code moved, which competitor, and which line of code keyed on the name.

Also report, before you start: **every place `product_name` is stored rather than joined.** If a saved generator run, a scenario snapshot or an export record carries a copy of the name, say so and leave it alone. A run made on 15 September recorded what the catalogue said on 15 September; that is a record, not a live view, and retro-editing it destroys the audit trail.

## A5. Provenance

A name change is a change. It gets the same treatment as a price:

- a `mrp_load_batches` row with the SHA-256, the row count and the timestamp
- the batch id recorded against each updated product
- old value and new value both retained, so the change is reversible
- attributed to the user who applied it
- visible in the audit trail

Undo must restore all 155 names in one action.

## A6. One thing to be aware of, not to fix

After the change, names in two of the three series are still not unique:

```
PPR Pipe      90 codes ->  3 distinct names
Casing Pipe   15 codes ->  2 distinct names
HDPE Pipe     50 codes -> 50 distinct names
```

Thirty products will read `Green Triple Layer Pipe (3 MTR)`. The `size` field is blank for all 155, so the only thing distinguishing them on screen is the code.

That is already true today and this change does not make it worse, so **do not invent a size or append one to the name.** Report it, and the human will take it to Prayag.

# JOB B — Indian digit grouping

Every rupee figure the application shows must group the **last three digits, then pairs**.

```
wrong    ₹100,000.00          ₹13,592,000.00        ₹1,352,320,560.20
right    ₹1,00,000.00         ₹1,35,92,000.00       ₹1,35,23,20,560.20
```

## B1. One shared formatter

Not scattered `toLocaleString()` calls — a single module every screen and every export goes through, so the next number added to the application is correct by default.

```js
// shared/format.ts

const inrMoney = new Intl.NumberFormat("en-IN", {
  style: "currency", currency: "INR",
  minimumFractionDigits: 2, maximumFractionDigits: 2,
});
const inrMoneyWhole = new Intl.NumberFormat("en-IN", {
  style: "currency", currency: "INR", maximumFractionDigits: 0,
});
const inrCount = new Intl.NumberFormat("en-IN", { maximumFractionDigits: 0 });

export const formatMoney      = (n) => inrMoney.format(n);
export const formatMoneyWhole = (n) => inrMoneyWhole.format(n);
export const formatCount      = (n) => inrCount.format(n);
```

This is a **locale change, not string logic**. Do not write a regex that inserts commas — `Intl` already knows the rule, handles negatives, and handles the crore boundary.

Verified output:

```
        318.24        ₹318.24                  (identical either way)
       1614.00        ₹1,614.00                (identical either way)
      25230.00        ₹25,230.00               (identical either way)
     100000.00        ₹1,00,000.00             was ₹100,000.00
    1352320.00        ₹13,52,320.00            was ₹1,352,320.00
   13592000.00        ₹1,35,92,000.00          was ₹13,592,000.00
 1352320560.20        ₹1,35,23,20,560.20       was ₹1,352,320,560.20
   -1080007.94        ₹-10,80,007.94           was ₹-1,080,007.94
```

## B2. Where it applies

Price Finder · product detail and price history · Comparison · Competition Analysis · MRP Generator input table, generated MRPs, run summaries, scenario comparison tab, collective margin values · Matching MRP view · Historical MRP series and tooltips · Single Price Editor · MRP upload preview and apply · every toast, banner and error that names a rupee figure. And counts that can exceed five digits.

## B3. What must never be grouped

| Never | Example |
|---|---|
| Years | `2026`, not `2,026` |
| Batch IDs | `batch 1946` |
| Product codes | `148-LSB`, `HD110D` |
| Percentages | `10.8%` |
| Any hash or commit id | — |

If a number is an **identifier**, it is never formatted. If it is a **quantity**, it is.

## B4. Exports — read this carefully

**Excel:** write the **raw number** and apply an Indian number format to the cell:

```
₹ with decimals    [$₹-en-IN]##,##,##0.00
₹ whole rupees     [$₹-en-IN]##,##,##0
plain count        ##,##,##0
```

If you write `"₹1,35,92,000.00"` as text, the column becomes unusable — `SUM` returns zero, and the Prayag team will not report it, they will simply stop trusting the file.

**CSV:** raw ungrouped numbers, no symbol. A comma inside a number breaks a comma-separated file.

## B5. What must not change

1. No stored value changes — not one row anywhere.
2. No arithmetic changes. Values are computed as numbers and formatted only at the edge. If any calculation currently parses a formatted string back into a number, **report it as a bug, do not preserve it**.
3. No API response changes. JSON carries numbers.
4. Input parsing is out of scope. If the editor accepts `100000` today it must still accept it. Report any field that would now reject a value pasted back from a display.

## B6. Do not verify Job B on Job A's products

The 155 products in Job A run from **₹44.50 to ₹9,890.60**. **None reaches ₹1,00,000.** The two grouping systems are identical below six digits, so these products will look unchanged — that is correct, not a failure.

Verify Job B on `WT-3LH-50` (₹1,00,000), on a generator run summary, and on a sales value pulled from the Sales API.
