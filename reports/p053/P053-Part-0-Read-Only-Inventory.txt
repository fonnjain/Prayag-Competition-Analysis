Only admin and user are present in stored accounts. counter is a recognized role in the existing user-management code but has zero stored accounts. No new role is needed or proposed.
Reuse artifacts/api-server/src/middlewares/authMiddleware.ts: requireAdmin, already used by the existing P048 vocabulary administration endpoints in priceEditor.ts.
Its production behavior: unsigned requests get 401; users requiring password replacement get 403 PASSWORD_CHANGE_REQUIRED; then:
  if (req.user.role !== "admin") {
    res.status(403).json({ error: "Admin access required." });
    return;
  }
Existing administrator-only examples include POST /api/catalog/price-editor/categories and POST /api/catalog/price-editor/series. The category-spelling read-only check also uses the same guard.
New private-list writes need explicit ownership authorization, not a blanket requireAdmin, because non-admins must be able to create/edit/delete their own lists. Setting everyone visibility must reuse the real admin role check. No product/price write permission is implied.

ACCESS DIFFERENCE THAT NEEDS A PAGE-PLACEMENT DECISION
The server's internal read routers are behind requireAuth and requireWorkspaceReadAccess, which permit all signed-in roles after password replacement. The Product Database UI in App.tsx, however, blocks user/counter and directs them to Price Finder. Admin-only maintenance routes retain their separate requireAdmin checks.
The two bucket pages therefore must either be narrow authenticated exceptions in Product Database, without opening the rest of that UI to non-admins, or live in Price Finder with sign-in required for list management. Existing anonymous Price Finder prices can remain anonymous; anonymous visitors have no user preference to retrieve. A personal active-list selection must never leak into anonymous or another user's results.

0.3 EXISTING SAVED FILTERS / RELATED FEATURES
No bucket-list, favourites or saved-view model was found in application code or the inspected production schema.
Price Finder does have persistent-in-the-URL comparison selection: repeated code query parameters, implemented in useSelection.ts/selectionState.ts. The coded limit is 50. It survives a reload of that URL and can be shared/bookmarked, but is not a named, owned, private or inherited list, and does not persist as a user's global preference.
Price Finder browse selection is React/context state. Speech-enabled preference is browser localStorage, not server per-user storage. Import recovery uses sessionStorage; authentication uses cookie/bearer session handling. These are not saved product sets.
MRP Generator has persisted scenarios in mrp_generator_scenarios: name, description, scope, rules, version, created_by, timestamps. They are administrator pricing-policy scenarios, not owned everyone/only_me included/excluded lists. Their GET list endpoint may ensure default scenarios, so it was not invoked during this read-only inventory. Their scopes/picker patterns may be reused, but repurposing the scenario model would couple bucket filtering to pricing policy and immutable generator history.
Recommendation: add a dedicated bucket model rather than redefine pricing scenarios or URL comparison selections.

0.4 PICKER SOURCE / REUSE
Use existing catalog_products:
- item_code, product_name for identity and display;
- division;
- category;
- series_range for optional Range;
- is_active and discontinued_from for live/inactive status.
This is the existing source retained by P049 Step 3, not a new source or a reclassification table. The master parser/planner already preserves existing classifications and uses the approved Range helper for new-product classification. No picker action should update these columns.
Reuse lib/formatting/src/index.ts: RANGE_DIVISIONS and supportsCatalogRange. Exactly three approved divisions: CP Fittings / Faucets, CP (QUAA / FERN), PTMT & Plastic Fittings. Do not create another division list.
Reuse artifacts/api-server/src/lib/priceEditorVocabulary.ts: normalizeVocabularyKey, already shared by vocabulary/category safety work. It handles NFKC, whitespace, case, punctuation/symbol spacing and the established simple singularisation. Rule matching must use this actual function, not a second approximation in SQL/client code. Resolve rules server-side against unchanged raw catalogue values.
Explicit case example:
Development at 2026-10-04 14:56:58 IST: CP Fittings / Faucets has 36 category Blaze 62 rows and 4 BLAZE 62 rows.
Production at 2026-10-04 14:57:03 IST: the same 36 + 4 rows.
A normalised Blaze 62 category rule therefore covers all 40; exact matching would miss 4. The BLAZE 62 rows have no Range; category matching must not require Range.
No HO rules have been created. The number of affected HO rules must be measured from the actual rules at the later seeding step, not invented now.

0.5 PER-USER STORAGE / SERVER IDENTITY
No dedicated per-user preferences/settings or active-list table/column was found in source or inspected production schema. discount_settings is a global scope/discount table, not per-user preferences. Activity tables have user_id but are telemetry, not settings. Do not repurpose session or activity records as durable list preferences.
Current identity is req.user.id, obtained by authMiddleware from the server-backed sessions table. getSessionId reads the sid cookie or Bearer session header; getSession loads the stored AuthUser. users.id is the stable ownership key. Do not use client-supplied owner IDs or mutable email as the ownership authority.
A new per-user active-list record will be needed for one global remembered selection, with server-side list visibility/ownership validation. Personal lists require sign-in; public anonymous pricing need not be removed.
